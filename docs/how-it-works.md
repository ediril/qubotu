# How it works

- **Local daemon.** One Python process (FastAPI, SQLite, Jinja, htmx) runs the agents and serves the UI, one per data folder. It answers only `127.0.0.1` and `localhost`, accepts changes only from its own pages, and requires the key in `~/.qubotu/ui.key`. Agents can reach `127.0.0.1` but can't read the data folder, so they can't drive the UI, for example to grant themselves a site's login.
- **Agents.** Each runs on Codex app-server in its own persistent thread and working folder, with web search and network access. Its commands run under a Codex permission profile: they write only their own folder and temp files and can't read your home folder (except `~/.gitconfig`). So even a web page that talks an agent into it can't get Qubotu's database, your Codex login, SSH keys, or the Keychain. Fireworks is a custom Codex provider.
- **Runs.** Every trigger (a chat message, the schedule, Run now, your answer, a help request) is saved to an inbox first, so it survives a restart. One agent's runs queue behind each other, at most three agents run at once, and a turn is interrupted after 30 minutes.
- **Tools and context.** Qubotu's tools (sharing, questions, help requests, memory, page browsing) are Codex dynamic tools. Codex fixes a thread's tools when it starts, so when they change, agents move to fresh threads and keep their chat, outputs, notes, and memory. Each run sends only what changed since the last one, plus older memories that match the message. After Codex compacts a thread, the full context goes again.
- **Collaboration.** `request_help` runs the other agent and returns its result to the requester, at most two hops deep.
- **Shared memory.** SQLite rows with local embeddings (fastembed, `bge-small-en-v1.5`), searched by cosine similarity plus FTS5 keywords. It sits behind a small interface, so a dedicated memory system can replace it.
- **Browser.** Playwright drives your installed Chrome, with your Chrome identity, at a person's pace. Agents get only page tools. Logged-out pages use a fresh context each time. Each logged-in site has its own profile in the data folder, where only GET, HEAD, and OPTIONS requests go out, to any host (GETs are trusted to be reads). WebSockets, service workers, and logout links are blocked, and a page that a redirect takes to another site is cleared. Local and private addresses are off-limits. A lock per site keeps a login window and an agent's tab off the same profile.
- **Blockers.** A login request or a blocking question shows on every page until you act. When a site's login window closes, every agent waiting on that site is answered, and the site goes to agents you approved or that already had it.
